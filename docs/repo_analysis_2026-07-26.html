Headline. The architecture and the scientific reasoning are sound — cross-engine refolding to defeat self-scoring bias is the right idea, and the installer solves a genuinely hard problem. The risk is not in the design, it is in the seams: seven defects cause the pipeline to silently produce or rank the wrong thing (§4.1), eight documented commands fail outright when you type them (§4.2), and the generated report describes a ranking method the code stopped using (§4.4). Most are a handful of lines each. Non-agentic operability is better than expected — the configurator's missing headless mode is the only true blocker (§3).

1. What this repository is

BinderScout (the package, CLI and docs all call it BindMaster) is an integration layer for GPU protein-binder design. It implements no design method of its own. It installs seven third-party design tools, generates run scripts for them from one interactive interview, then cross-validates whatever they produce by re-folding the designed sequences with independent structure predictors and ranking the results.

Two parts carry the value:

  • The installer (install/install.sh, 2752 lines) — makes seven mutually incompatible CUDA/JAX/PyTorch stacks coexist on one host, including a from-source aarch64 path and a standalone mode needing no system permissions. This is hard, unglamorous work and it is mostly good.
  • The Evaluator (Evaluator/binder_comparison/, 22 subcommands) — a cross-engine scoring pipeline built on a correct insight: a design engine's own confidence score is gameable by the engine that produced it, so ranking must come from independent refolders.

The configurator sits between them, and is where most of the serious defects live.

2. Data flow

target.pdb / .mmcif │ ├─▶ configurator/configurator.py [system python, stdlib] 80 questions, 14 screens │ writes runs/<name>/ │ ├── run_<tool>.sh one per enabled tool │ ├── run_all.sh sequential driver ← breaks with Mosaic (F8) │ ├── run_evaluate.sh wrapper on evaluate.sh ← wrong RFD3 path (F3) │ └── bindcraft/target_settings.json │ ├─▶ run_all.sh ─▶ 7 design tools, each in its OWN environment │ BindCraft │ BoltzGen │ Mosaic/.venv │ bindmaster_pxdesign │ │ Proteina-Complexa/.venv │ bindmaster_protein_hunter │ bindmaster_rfd3 │ raw output ─▶ runs/<name>/<tool>/… (designs.csv, summary_high_iptm.csv, *.cif.gz, …) │ ├─▶ binder-compare extract [binder-eval] │ one extractor per tool ─▶ dedup by sequence ─▶ sequences.fasta │ ⚑ JOIN KEY from here on is the amino-acid sequence string, not a design id │ ├─▶ (optional) binder-compare filter-soluprot [binder-eval-soluprot, py3.7] │ ├─▶ refold — each engine writes its own CSV: │ Boltz-2 ─▶ boltz2_results.csv [Mosaic/.venv] │ AF3 3.0.2 ─▶ af3_results.csv [binder-eval-af3, >100 GB VRAM] │ ESMFold2 ─▶ esmfold2_results.csv [binder-eval-esmfold2] ← documented default │ Protenix ─▶ protenix_results.csv [bindmaster_pxdesign] ← "optional", but opt-OUT (F4) │ all read ONE shared target MSA: ~/.cache/bindmaster/target_msa/target_<sha256[:16]>.a3m │ ├─▶ comparison/merger.py outer-join every engine CSV ON sequence ← fan-out risk (F6) ├─▶ comparison/scoring.py iPSAE · PAE-recomputed per-engine iPTM · │ consensus_iptm (max) / _mean · two-stage rank ← F5, F7 └─▶ visualization/report.py report.html + CSV + NGL 3D viewer ← CDN dependency (F19)

The one structural weakness: the join key is the sequence string. It is a defensible choice (each engine independently folds a sequence, so the sequence is what they share) but it makes every downstream merge sensitive to duplicate sequences — see F6.

3. Non-agentic mode — can a human run this without an LLM?

This was the main question, and the answer is mostly yes, with one hard blocker. The executable pipeline has zero runtime LLM dependency: no anthropic, openai or model-endpoint call exists anywhere in bindmaster.py, configurator/, install/ or Evaluator/. The five .claude/skills/ packages are an operating manual, not a dependency.

Works with gaps
Installer

bash install/install.sh --tool all --yes --skip-examples is genuinely non-interactive. But it is destructive on re-run (F11), has no preflight, and on aarch64 three tools cannot be installed at all (F12–F14).

Blocked
Configurator

The entire flag surface is --archive and --status. No --config, no --headless, no json.load anywhere in the 3593-line file, and the cfg dict is never serialised. A cron job cannot produce a run directory.

Works
Evaluator

Evaluator/evaluate.sh is a real orchestrator: engine auto-detection, graceful skip with a printed note, --resume, standalone-conda discovery, per-engine env overrides. The gap is documentation, not capability.

3.1 The deterministic machinery mostly exists — it is just undocumented for humans

The hypothesis going in was that campaign logic lives as prose in the skill files. That turned out to be largely wrong: the code is better than its documentation. Two examples that matter:

  • The autosize loop is real code, not prose. run_autosize_loop() (comparison/autosize.py:134) drives generate → score → decide with a budget_cap, max_rounds and a margin, exposed as binder-compare autosize --loop --generate-cmd …. It appears once in README and zero times in the skills.
  • Gate tiers are code (GATE_TIERS, same module), not a threshold the operator has to recall.

What genuinely is LLM-only is the documentation of the CLI, and that is measurable. Counting literal binder-compare <cmd> invocations:

The cheapest high-value fix in this report. Two of three modules already run headlessly. Add configurator --config run.json (dump the cfg dict on every wizard exit; load it to skip all prompts) plus one "Operator's manual" page listing all 22 subcommands, and the system moves from "needs an operator who has read the skills" to "runnable from a shell script or cron". That is roughly 150 lines and one markdown page — cheaper than any GUI (§5), and a prerequisite for one.

4. Findings

31 findings, grouped by consequence. documented marks issues already in CLAUDE.md's "Known issues" that are still unfixed and still affect results.

4.1 Silently wrong science — these change which designs you would order

Critical  F1 · The mmCIF chain answer is discarded; the longest entity is used as the target

configurator/configurator.py:551 — extract_sequence_from_cif(cif_path, chain_id)

The function tries two branches in the wrong order:

  • Branch 1 — _cif_entity_poly_seq(text) (:454) takes no chain argument, and its docstring says it extracts the longest canonical one-letter sequence from _entity_poly. The call site's own comment concedes it: # Try canonical _entity_poly first (chain-agnostic, longest entity).
  • Branch 2 — the inline _atom_site loop (:556–599) is chain-aware: if ch.upper() != chain_id.upper(): continue at :584. But it only runs when branch 1 returned nothing.

Since essentially every PDB-derived mmCIF carries _entity_poly, branch 1 nearly always wins and the chain answer is discarded.

Failure: Step 3 asks "Chain(s) to target", the user answers A for a 100 aa antigen in an antibody–antigen mmCIF, and the 220 aa heavy chain is silently used instead. Every one of the seven tools then designs against the wrong protein and the Evaluator refolds against it too, so the run is internally consistent and confidently scored. Nothing in the output reveals it — the wizard even prints ✓ Auto-extracted sequence for chain A. The residue count on that line is the only signal.

Fix (implemented): try the chain-aware _atom_site branch first and fall back to _entity_poly only when the requested chain has no coordinates, printing an explicit warning that names the chain and the fallback length. extract_sequence_from_pdb (:364) already filtered correctly, so .pdb input was never affected.

Note. A separate helper _cif_atom_site_seq (:497) is labelled "for requested chain" but takes no chain argument and would concatenate every chain. It is dead code — nothing calls it — so it is not part of this defect. Flagged rather than deleted, per the repo's own guidance on pre-existing dead code.

High  F2 · Mosaic epitope indices always resolve against chain A

configurator/configurator.py:913 — chain = cfg.get("target_chain") or cfg.get("chain") or "A"

Neither cfg["target_chain"] nor cfg["chain"] is ever assigned. The wizard only writes cfg["chains"] (plural, :803, :826), so the fallback "A" is used on every run.

Failure: target is a two-chain complex, the user selects chain B and hotspots 32,36,39. hotspots_to_epitope_idx resolves those residue numbers against chain A's numbering, so Mosaic hallucinates against a different surface than the one requested. Silent — the run looks normal and the designs look fine.

Fix: read the primary chain from cfg["chains"] (first entry), the same value Step 3 stores.

High  F3 · RFD3 designs never reach the Evaluator

configurator/configurator.py:2459 — design_dirs.append(("--rfd3", str(run_dir / "rfd3" / "outputs")))
but :1963 RFD3_DIR="$RUN_DIR/rfd3" and :1610 check_outputs "$RUN_DIR/rfd3/sequences.csv"

The generated run_evaluate.sh points the extractor at rfd3/outputs, and :2623 dutifully creates that directory — but nothing ever writes into it. run_rfd3.sh writes rfd3/sequences.csv one level up, which the same file's run_all.sh generator correctly checks. RFD3Extractor._find_csv searches input_dir and input_dir.rglob(); it never walks upward.

Failure: a completed RFD3 run (23 h on a 24 GB Ampere, per CLAUDE.md's own notes) contributes zero designs to the report, with no error — the extractor just finds an empty directory. Two lines of the same file disagree about the path.

Fix: str(run_dir / "rfd3"), matching :1610; drop the :2623 mkdir.

High  F4 · Protenix silently joins the consensus, contradicting the docs three times over

Evaluator/evaluate.sh:135–143 — SKIP_PROTENIX starts at 0 and is set to 1 only when the env is missing

CLAUDE.md states the opposite in three places: "Protenix runs only when explicitly enabled" (:125), "evaluate.sh orchestrates Boltz-2 + AF3 + ESMFold2 by default" (:197), and "Opt-in via evaluate.sh flags; not part of the default Boltz-2 + AF3 + ESMFold2 pipeline" (:359). The code is opt-out. Note that README's engine table is correct here — "evaluate.sh auto-detects and runs whichever engine envs are present" — so the contradiction is CLAUDE.md against both the code and the README.

Failure: bindmaster install --tool all creates bindmaster_pxdesign, so on any full x86 install evaluate.sh runs a fourth, unrequested GPU refold pass over the whole pool — then folds protenix_pae_iptm into consensus_iptm and consensus_iptm_mean, the primary two-stage ranking. Two operators with identical designs get different rankings depending on whether they happened to install PXDesign. That is a reproducibility break in the headline metric.

Fix: default SKIP_PROTENIX=1 and add --with-protenix, or correct the three documentation claims. Either is fine; the current mismatch is not.

High  F5 · Single-engine designs are ranked against multi-engine designs on the same scale

Evaluator/binder_comparison/comparison/scoring.py:828–836
sort_keys = ["passes_max_screen", "consensus_iptm_mean", "consensus_iptm"] — consensus_iptm_n is computed at :713 and never used in the sort

DataFrame.mean(axis=1) skips NaN, so a design only Boltz-2 refolded gets consensus_iptm_mean equal to its single Boltz iPTM, competing directly with means over three engines.

Failure: Mosaic is Boltz-2 gradient hallucination, so a Mosaic design AF3 never saw can pass the max screen and top the mean rank on the strength of the one engine that is biased in its favour. This violates the repo's own stated rule — "iptm is gameable by the designing engine … Never rank on a single engine's ipTM" (CLAUDE.md, Critical domain facts). The mechanism designed to prevent exactly this is not enforced.

Fix: require consensus_iptm_n >= 2 for passes_max_screen, and/or add consensus_iptm_n as a leading sort key so multi-engine agreement outranks single-engine confidence.

High  F6 · Duplicate sequences fan out report rows and shift the screen threshold

comparison/merger.py:68 pd.merge(…, on="sequence", how="outer")
merger.py:127 pd.merge(df, meta_df, on="sequence", how="left") — no drop_duplicates, no validate=

Two FASTA entries with the same sequence but different binder_id put two rows in meta_df, and the left merge then duplicates every matching metrics row.

Failure: one design occupies two Top-30 slots with identical metrics, and n_eligible inflates so the top-50% screen threshold moves. extract dedups by default, but --keep-duplicates (cli/extract.py:195) re-enables the hazard, and append-mode refold CSVs can carry duplicate rows independently. Telling detail: cli/autosize.py:160 already guards the analogous merge with .drop_duplicates("sequence") — the defence exists, in the wrong file.

Fix: the same .drop_duplicates("sequence") on meta_df, plus validate="m:1" so a future regression raises instead of inflating.

Medium  F7 · The Mosaic column-mismatch "Fix" does not fix misalignment documented

extractors/mosaic.py:43–68 — docstring claims "Fix: … extend the header with anonymous extra columns … The named columns … stay correct since they're always in the same position", while :89 says the extra columns are "inserted after the sequence column"

Padding the header at the end cannot realign rows whose extra columns were inserted in the middle. For those rows every field after sequence shifts by two.

Failure: is_top reads a neighbouring column's value, so the is_top == 1 filter (:101) selects the wrong ~40 designs out of ~800 for refolding. The code prevents row dropping only; the docstring overstates it, which is worse than not fixing it, because a reader stops worrying.

Fix: detect the wide-row header variant and reindex per row, or fail loudly on a column-count mismatch. At minimum correct the docstring.

4.2 Documented commands that fail when you type them

High  F8 · run_all.sh exits 1 before any tool runs, whenever Mosaic is enabled

configurator/configurator.py:1556–1567 — the Mosaic block is emitted first and ends in exit 1 unless mosaic/designs.csv already exists

Failure: bash runs/<name>/run_all.sh is the documented one-command way to execute a campaign (CLAUDE.md:429, README.md:196). On a fresh run directory with Mosaic enabled — a normal choice — it prints "Mosaic requires interactive input" and exits 1 before BoltzGen, BindCraft, RFD3 or Protein-Hunter start.

Fix: emit the Mosaic block last, or continue past it with a warning instead of exit 1.

High  F9 · "Run the pipeline now?" silently skips RFD3 and Protein-Hunter

configurator/configurator.py:2662 — run_pipeline() branches on mosaic, boltzgen, bindcraft, pxdesign_local, proteina_complexa and evaluator

No branch exists for rfd3 or protein_hunter — the Part L and Part M additions — even though tools_enabled carries those keys (:2994–2995) and generate() writes run_rfd3.sh and run_protein_hunter.sh. The same two are missing from the Step 7 preview tree (print_tree, :743, which also omits Proteina-Complexa) and from the "To run later" list (:3423), so a user who enables them is never even told the scripts exist.

Failure: a user enables RFD3 + Protein-Hunter + Evaluator and answers "y" to "Run the pipeline now?" (the default). Nothing runs for either design tool; the Evaluator then runs on an empty pool and emits a report with no designs. No error, no warning.

Fix: drive the loop from tools_enabled and the generated run_<tool>.sh files rather than a hand-maintained if-chain — and do the same in print_tree and the next-steps block.

High  F10 · The installer's own evaluate shortcut always fails

Evaluator/run.sh:91 passes --target-pdb "$TARGET_PDB"; Evaluator/evaluate.sh:116 is *) echo "Unknown argument: $1"; exit 1 ;; and has no --target-pdb case

Failure: a human runs evaluate (the shortcut both installers write, install.sh:1192), pastes their sequences, gives a target PDB, accepts the output directory, waits while the target sequence is extracted — and evaluate.sh dies immediately with Unknown argument: --target-pdb. The documented human entry point to the Evaluator has never worked; you must know to call evaluate.sh directly with --target-seq and a bare amino-acid string.

Fix: drop the --target-pdb line from run.sh (it already computes $TARGET_SEQ), or accept and ignore the flag in evaluate.sh.

High  F11 · --yes turns every "reuse existing?" prompt into rm -rf

install/install.sh:282 — confirm() returns 0 unconditionally when AUTO_YES=true
install/install.sh:706 — if confirm "Remove and reclone?"; then rm -rf "${BINDCRAFT_DIR}"

The prompt renders as [y/N] — default no — but --yes forces yes, inverting the displayed default on precisely the destructive prompts.

Failure: bash install/install.sh --tool all --yes --skip-examples is the documented non-interactive command (CLAUDE.md Commands, Dockerfile.test:60, test_env.sh:136) and the skills' recommended repair step. Run it a second time on a working machine and it deletes BindCraft/, including params/*.npz — roughly 4 GB of AF2 weights that Proteina-Complexa symlinks against. A re-install is not idempotent; it is lossy.

Fix: give destructive prompts their own helper that keeps the [y/N] default under --yes, and gate reclone/re-create behind an explicit --force.

High  F12 · The aarch64 installer rejects rfd3, proteina-complexa and protein-hunter

install/install_aarch.sh:81–100 — accepted values are all, bindcraft, boltzgen, mosaic, evaluator, pxdesign, af3, esmfold2, soluprot

CLAUDE.md states "Part M — RFD3 installable via bindmaster install --tool rfd3 (x86 + aarch64)" and "RFD3: fully supported on aarch64 (no DGL dependency; pip-installs cleanly)".

Failure: on a DGX Spark, bash install/install_aarch.sh --tool rfd3 exits 1 with Invalid --tool value: rfd3. There is no way to install a feature documented as landed and supported. Proteina-Complexa is in the same position; Protein-Hunter is legitimately aarch64-blocked (PyRosetta) but the error message does not say so.

Fix: add the rfd3|foundry and proteina-complexa cases, or correct the support matrix. For Protein-Hunter, print the PyRosetta reason instead of "Invalid --tool value".

High  F13 · --tool all on aarch64 omits the default refold engine

install/install_aarch.sh:82 — sets DO_BINDCRAFT · DO_BOLTZGEN · DO_MOSAIC · DO_EVALUATOR · DO_PXDESIGN only

CLAUDE.md describes ESMFold2 as the "Default refold engine — installed by --tool all".

Failure: an aarch64 user who runs --tool all gets no ESMFold2 env, so evaluate.sh prints "will be skipped" and consensus_iptm is computed from fewer engines than the ranking design assumes — which, given F5, changes the ranking rather than just shrinking it.

Fix: add DO_ESMFOLD2=true to the aarch64 all case.

High  F14 · The aarch64 ESMFold2 install pins a package the x86 installer documents as nonexistent

install/install_aarch.sh:1740 — pip install -q esmfold gemmi
install/install.sh:2245 — # NOTE: there is NO `esmfold` PyPI package. The runtime is transformers' ESMFold2Model + biohub's `esm` SDK … + gemmi …

The x86 path installs four things the aarch64 path omits entirely: torch (from an already arch-aware index — install.sh:2249 selects cu130 for aarch64), transformers>=4.50, safetensors, and esm @ git+https://github.com/Biohub/esm.git@c94ed8d. The env yml supplies only python 3.12, pip and numpy.

Failure: on DGX Spark, --tool esmfold2 either hard-fails on the bogus requirement or produces an env with no torch and no esm SDK, where refold-esmfold2 dies at import. The --help-only smoke test (:1747) can still pass, so the installer may report success. Combined with F13, the documented default refold engine is doubly unavailable on the flagship platform.

Fix: delete the aarch64 copy and call install.sh's install_esmfold2() — it is already architecture-aware. This is duplication drift, not a platform limitation.

High  F15 · The provenance block kills every run script on a host without nvidia-smi

configurator/configurator.py:1157–1158
GPU_NAME=$(nvidia-smi --query-gpu=name --format=csv,noheader -i {gpu_id} 2>/dev/null | head -1)
— while the neighbouring GIT_SHA, GIT_BRANCH and PY_VER are guarded with || echo "unknown"

Every generated script starts set -euo pipefail. Reproduced here:

$ cat t.sh
set -euo pipefail

echo "REACHED-AFTER-GPU_NAME"
$ bash t.sh

Failure: on a CPU login node, in a container without the NVIDIA runtime, or with a wrong --gpu-id, the run scripts for PXDesign, Proteina-Complexa, RFD3 and Protein-Hunter die at the provenance block before the design step. The block added to improve reproducibility is the thing that stops the run — and only the four tools that have it are affected (see F28).

Fix: append || echo "unknown" to the GPU_NAME and GPU_MEM assignments, matching the three lines above them.

Medium  F16 · No architecture dispatch in any entry point

bindmaster.py:105 script = REPO / "install" / "install.sh"; tui/app.py:259, 418 hardcode the same path

Failure: a DGX Spark operator following README:391 runs bindmaster install --tool all and silently gets the x86_64 installer — CUDA defaulting to 12.4 instead of 13.0, conda asked for pytorch-cuda=12.4 and gcc_linux-64 (no linux-aarch64 builds), and none of the aarch64 patches applied. install.sh:2615 warns but proceeds.

Fix: in _dispatch, select install_aarch.sh when platform.machine() == "aarch64"; have the TUI call the same dispatcher.

Medium  F17 · The skills prescribe a recovery flag that does not exist

.claude/skills/bindmaster-worker/references/troubleshooting.md:238 and references/tools/pxdesign.md:21 and .claude/skills/bindmaster-orchestrator/references/evaluation.md:216 — "rerun install/install.sh --pxdesign to reapply the patches"

Failure: this is the documented recovery for the exact failure CLAUDE.md's Known Issues warns about ("patches … would be lost if packages are upgraded manually"). Typing it yields Unknown option: --pxdesign, exit 1. The correct form is --tool pxdesign, which per F18 then aborts at conda create anyway.

Fix: correct all three references to --tool pxdesign, and add a genuine --reapply-patches path.

4.3 Robustness, reproducibility and hygiene

#SevFindingLocationConsequence & fix
F18Med PXDesign install is not resumable — no env_exists guard, so any re-run aborts at conda create install/install.sh:1236 install_pxdesign is a ~25-step function whose later steps are all network-bound (Protenix, PXDesignBench, ColabDesign, deepspeed, CUTLASS, weights). When one drops out — the common case — the operator's natural re-run fails immediately instead of resuming. Fix: the env_exists + skip pattern already used for binder-eval-esmfold2.

4.4 Report truthfulness and shortlist integrity

These concern what the generated report.html and top30_candidates.csv tell you — the artefacts a scientist actually reads before spending money on synthesis.

High  F32 · Every report describes a ranking method the code no longer uses

visualization/report.py:1837–1846 (the rendered two_stage methodology block) vs cli/report.py:346 screen_metric = getattr(args, "screen_metric", "max") or "max"

The report tells the reader, verbatim: "Ranking is two-stage mean iPTM … Stage 1 — screen: consensus_iptm_mean = mean(boltz2, af3, esmfold2 iPTM) … Mean was selected as default over max because it is more robust to per-target engine blind spots … The legacy max-screen (--screen-metric max) is the precision-leaning alternative … so Stage 1 + Stage 2 collapse to a single mean-iPTM gate-then-rank."

Every one of those statements is now false. Commit 5769064 ("evaluator: revert two-stage screen default to max") changed the default back to max — and git show --stat confirms it touched CHANGELOG.md, CLAUDE.md, cli/report.py, comparison/scoring.py and test_scoring.py, but not visualization/report.py.

Failure: every report.html generated on current master runs a max screen while its own methodology section says it ran a mean screen, calls mean "the default", calls max "legacy", and claims the two stages "collapse to a single mean-iPTM gate-then-rank" — precisely the behaviour the revert was meant to undo. A scientist deciding what to order is reading the wrong method, with benchmark AUC numbers attached to lend it authority. Arguably the most consequential drift in the repository, because it is embedded in the deliverable rather than in a doc someone might skip.

Fix: render the methodology text from the actual screen_metric argument instead of a hardcoded string, so it cannot desync again.

5. GUI options

The honest recommendation is do the config-file work first and the GUI second. Most of what feels like a UI problem here is a state problem: there is no machine-readable description of a run, so every front-end has to re-ask 80 questions. Fix that and a GUI becomes a thin optional layer; skip it and every GUI inherits the wizard's shape.

OptionWhat it isEffortVerdict
A · Richer curses TUI
extend tui/app.py		 Stays stdlib-only and works over bare ssh with no port forwarding. Add a form-based run editor, a live log tail, and per-tool progress to the existing 5-item menu. ~2–3 wk Works everywhere, but hand-rolling curses forms for 80 fields is a lot of widget code for a modest payoff, and it can never show structures or plots.
B · Local web UI
one Python process + ssh port-forward		 A stdlib http.server-class app (or a small FastAPI) serving four routes and shelling out to the existing CLI. Reuses visualization/report.py and the vendored NGL viewer, so results rendering is already built. ~1 wk for phase 1 Recommended — see below.
C · Config-as-JSON + static status page
no server at all		 configurator --config run.json for input, and binder-compare status --html writing a static file you scp or open locally. No process to keep alive, no port, nothing to secure. ~2–3 days Best value per line in this report, and a strict prerequisite for A and B. Do it first.

Why B, and what phase 1 looks like

The decisive argument for the browser is that the hard part is already done. visualization/report.py already emits a self-contained HTML report with base64 plots, sortable metric tables and an NGL structure viewer, and tools/ngl/ is already vendored. A web UI does not need a charting stack or a 3D viewer — it needs a shell around artefacts that already exist. Neither A nor C can show the structures at all.

Phase 1, deliberately small — target under 400 lines, stdlib http.server only:

RouteShowsCalls
GET / Run list: name, tools configured, design counts, evaluated yes/no the same runs/ scan as configurator.cmd_status() — reuse it rather than reimplement, and fix F27 in the process
GET /run/<name> Per-tool status, last 200 lines of each run.log, the settings.json provenance block file reads only, no subprocess
GET /run/<name>/report The existing report.html, served as-is nothing — it is already a file on disk
POST /run/<name>/evaluate Fire-and-forget, streaming the log back to /run/<name> subprocess.Popen(["bash", run_dir/"run_evaluate.sh"]) — the wrapper the configurator already generates

That is useful on day one, from a laptop over ssh -L 8765:localhost:8765, with no new dependency. Phase 2 adds a run editor reading and writing the run.json from option C — which is why C comes first. Phase 3, only if wanted, adds a cross-machine queue view.

The multi-env and multi-day problems

  • Environments: the UI should never activate a conda env. It launches run_evaluate.sh / run_all.sh, which already do standalone-vs-system conda discovery (evaluate.sh:36–45). Keeping that in one place is why this stays small.
  • Multi-day runs: never hold a connection. Poll artefacts on disk — the per-tool output dir, settings.json, run.log — exactly as the TUI status screen does. A server restart then costs nothing, which matters when jobs outlive ssh sessions.

What a GUI should not do here

  • Not run the installer. It is a 2752-line interactive bash script that wants a terminal for progress. --tool all --yes already covers automation (once F11 is fixed).
  • Not reimplement scoring or plots. Everything must go through binder-compare, or the report and the UI will drift apart — the same drift that produced F20 and F27.
  • Not become the only way to configure a run. That is today's problem with a nicer skin. run.json stays the source of truth, with the GUI as one editor among several (wizard, hand-edited file, cron).
  • Not listen on a public interface. Bind 127.0.0.1 and require an ssh tunnel. It runs shell commands as the user; there should be no auth surface to get wrong.

6. What is already good

Worth stating plainly, because several things here are better than the documentation suggests:

  • The core scientific insight is right. Ranking on independent refolders rather than the designer's own confidence is correct, and the two-stage max-screen → mean-rank design (scoring.py:790) is a thoughtful answer to a real problem. F5 is a gap in enforcing it, not a flaw in the idea.
  • evaluate.sh is a genuinely good orchestrator — engine auto-detection, graceful skip with a printed note, --resume, standalone-conda discovery, per-engine env overrides. This is what non-agentic operability should look like everywhere else.
  • The autosize loop is real code with a budget cap and a round limit (comparison/autosize.py:134) — not an LLM-driven loop. It deserves documentation.
  • The shared MSA cache design is sound and solves a real rate-limit failure across three engines; F21 and F22 are refinements to a correct idea.
  • Both documented extractor traps are genuinely handled in code — BoltzGenExtractor prefers designed_chain_sequence (boltzgen.py:38), and the Mosaic reader widens the header rather than dropping rows (F7 is about how far that goes, not whether it was attempted).
  • ~200 unit tests on the comparison layer, plus shellcheck and ruff in CI, and a "Known issues" section that is unusually honest about its own limitations.

7. Suggested order

  1. Stop producing wrong answers — F1 (chain selection), F2 (hotspot chain), F3 (RFD3 path), F4 (Protenix default), F5 (engine-count gate), F6 (merge dedup), F23 (ceil), F33 (AF3 ipSAE missing from the shortlist). These change which designs a wet lab is told to order. F1 is the one to fix today.
  2. Make the report tell the truth — F32 (methodology text describes the reverted mean-screen), F34, F35, F36. F32 is a one-line change and it is currently misinforming every reader of every report.
  3. Unbreak the documented commands — F8, F9, F10, F11, F15, F17. All small; all currently fail for anyone following the README.
  4. Fix the aarch64 matrix — F12, F13, F14, F16. Cheap, and they block the flagship platform. F14 is deletion, not new code.
  5. Close the non-agentic gap — configurator --config run.json plus an operator's manual covering all 22 subcommands. Highest leverage item in the report, and it unlocks the GUI work.
  6. Close the ingestion holes — F38 (run missing three tools), F39 (RFD3 FASTA fallback), F40 (zero-yield is not an error), F41 (Evaluator README documents a deleted engine), F42, F43. These decide whether a tool's designs appear in the report at all.
  7. Then robustness and provenance — F18–F22, F24–F26, F28.
  8. Then hygiene — F29 + F37 (test the live extractors and the two scoring kernels), F30 (third-party notices), F31.
  9. GUI last — option C, then web-UI phase 1.
